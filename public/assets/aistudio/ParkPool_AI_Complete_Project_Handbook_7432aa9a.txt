# ParkPool AI — Combined Project Master Pack

**Working title:** ParkPool AI  
**Product:** Intelligent Shared Parking Coordination Platform  
**Tagline:** Smart parking. Shared possibilities.  
**Version:** 2.0 — combined project baseline  
**Status:** Proposed product and architecture; not a completed or production-validated application.

## What this package contains

This package combines two source concepts:

1. **Parking Pooling System — Project Handover & Discussion Summary**: the practical India-focused marketplace and its real-world operating concerns.
2. **ParkPool AI — Complete Project Pack**: the 12-module architecture, 12 specialist-agent proposal, optimization, evaluation, technology and implementation plan.

The combined product keeps the practical marketplace and operations from the handover, then adds an intelligence and optimization layer. The original source documents are preserved in `source_material/` and the original ParkPool AI documentation remains in `docs/`.

## The combined product in one paragraph

ParkPool AI is an India-focused, web-first shared-parking marketplace and coordination platform. It connects drivers with verified, legally authorized private, residential-community and commercial parking providers. Drivers discover nearby spaces, compare actual walking routes, prices, vehicle fit and source-stamped availability, then book and manage a parking session. Providers control their inventory, schedules, buffers and access rules. A hybrid intelligence layer uses deterministic services and mathematical optimization for availability, matching, booking and allocation, while specialist AI agents interpret requests, coordinate tools, summarize evidence and explain recommendations. Confirmed bookings remain protected by transactional backend rules.

## The central product decision

**The marketplace is the product foundation; reliable distributed time-window coordination is the core technical differentiator.**

Do not position this as merely another parking listing app or claim that it is the first AI parking platform. Parking discovery, private-space rentals, shared-parking allocation and multi-agent parking research already exist. The proposed contribution is the integrated implementation and experimentally evaluated combination of:

- distributed provider coordination;
- provider authorization and property-level constraints;
- time-window pooling with buffers and owner-use periods;
- uncertainty-aware allocation and controlled reallocation;
- deterministic booking integrity;
- hybrid AI-agent plus mathematical-optimization architecture;
- evidence-grounded, explainable recommendations;
- evaluation against simple baselines.

This is a proposed differentiation, not proof of global novelty, patentability or commercial success.

PARKING POOLING SYSTEM
Project Handover & Discussion Summary
India-focused concept | Initial example: Phoenix Mall of Asia, Bengaluru
1. Purpose of this document
This document captures the key points from an earlier brainstorming discussion about a Parking Pooling System. It is intended to be shared with a teammate or uploaded to another AI assistant so the project can continue without repeating the original background.
Important: this is an early concept and discussion handover, not a validated business plan, legal opinion, final product specification, or proof that the proposed model is commercially viable.
2. Core idea
Build a location-based marketplace that connects people who need temporary parking with individuals or organisations that have legally usable, underutilised parking spaces near busy destinations. A space owner/host lists availability for specific time slots; a driver discovers, books, pays for, and navigates to that space.
The concept is similar to pooling or sharing unused parking capacity. It is not carpooling: the vehicle remains with its driver, and the platform coordinates access to a parking space.
3. Problem being addressed
•	Parking demand becomes high around malls, offices, hospitals, event venues, markets and other busy destinations.
•	Drivers may waste time searching for a space, face congestion, or find official parking full or inconvenient.
•	At the same time, some homes, apartments, offices and commercial properties may have parking capacity that is unused during certain hours.
•	The platform aims to make this unused capacity discoverable and bookable, while giving hosts a way to earn from available space.
4. Example use case discussed
A person is visiting Phoenix Mall of Asia in Bengaluru. Mall parking may be crowded, full, or inconvenient. The driver opens the platform, searches around the mall, compares nearby verified parking spaces by price, availability and walking distance, books a suitable time slot, and follows directions to the actual parking entrance. A nearby property owner earns money for making the space available.
5. Main users and stakeholders
•	Driver / customer: searches for a space, books a slot, provides vehicle details, parks and leaves.
•	Host / space owner: lists a space, sets availability and price, approves or manages bookings, and receives earnings.
•	Property manager / authorised commercial partner: may provide multiple spaces and control access.
•	Platform administrator / support team: verifies listings, handles disputes and incidents, monitors bookings and manages refunds.
6. Proposed end-to-end user flow
1.	Discover: Driver enters a destination and date/time. The platform displays available spaces nearby.
2.	Compare: Driver checks the exact location/entrance, walking route and estimated walking time, price, space type, restrictions and availability.
3.	Book: Driver selects a time slot and enters required vehicle details. Booking rules, cancellation terms and any deposit/fees are shown before confirmation.
4.	Navigate: The app guides the driver to the correct property entrance and parking bay—not merely to a map pin.
5.	Verify arrival: A booking code or QR/access verification can help confirm that the correct customer has arrived. The host/property controls actual access.
6.	Park and manage session: The session is recorded as started. The customer can view the end time and request an extension if available.
7.	End session: The driver leaves and the booking is marked complete, subject to the agreed check-out process.
8.	Payment and feedback: The platform issues a receipt, processes the applicable payment/refund, and allows reviews or incident reports.
7. Features discussed or proposed
Customer / driver
•	Search parking by destination or map location.
•	See available spaces, time slots, price and walking distance/time.
•	View photos, dimensions, vehicle restrictions, access instructions and host/property details.
•	Book, pay, cancel and receive booking confirmation/receipt.
•	Get directions to the real entrance and parking bay.
•	View active booking, end time, extension status and booking history.
•	Contact support, report an incident and leave a review.
Host / property
•	Register and submit proof of identity/authority to list the space.
•	Add space details, photos, access instructions, restrictions and pricing.
•	Set availability by date/time and block unavailable periods.
•	View, approve or manage bookings where manual approval is required.
•	Set a hard latest departure time and a buffer before the space is needed again.
•	View bookings and earnings.
Admin / operations
•	Verify hosts, properties and parking listings before they go live.
•	Review suspicious listings, complaints, disputes and incident reports.
•	Manage cancellations, refunds, overstay cases and customer support.
•	Monitor booking completion, no-shows, late departures and host reliability.
•	Maintain an auditable record of booking and access events.
8. Major problems and concerns raised
Security and criminal misuse
•	Concern: Concern: What if a customer parks a vehicle containing explosives, weapons, contraband or other dangerous/illegal material on a host's private property? The host may face danger, investigation or liability even if they did not know what was inside.
•	Possible handling discussed: Discussion direction: verify the host and their authority to list the property; collect booking and vehicle details; use controlled check-in/access records; provide a clear suspicious-activity and emergency reporting process. Do not claim that the platform can security-clear a vehicle or guarantee that misuse is impossible. Never advise a host to inspect dangerous contents or handle a suspected device. Keep people away and contact emergency services/police (112 in India) when there is an immediate threat.
•	Open question: Still unresolved: the platform's legal responsibility, the host's responsibility, what checks are lawful and proportionate, insurance coverage, and how law enforcement would be contacted.
Late departure / host needs the space back
•	Concern: Concern: A host rents a space until 6:00 PM, but the driver has not removed the vehicle by 7:00 PM. The host may need to leave or use the space at 6:15 PM. This can create a direct conflict and may trap or inconvenience the host.
•	Possible handling discussed: Discussion direction: use fixed booking slots; require a host-defined buffer before the host needs the space; record a hard latest departure time; allow extensions only when the host explicitly approves and the next booking does not conflict; show overstay charges and escalation/support rules before booking.
•	Open question: Still unresolved: how to handle a vehicle that remains after the host's hard deadline, what lawful remedies exist, who pays for resulting losses, and how to avoid unsafe or unlawful towing/clamping. Do not assume the host can forcibly move or tow a vehicle.
Walking distance and customer willingness
•	Concern: Concern: Will a customer really park 300–500 metres away from a mall or destination instead of using the destination's own parking? A cheaper space may not be attractive if the walk is inconvenient, unsafe, poorly lit, inaccessible or difficult in bad weather.
•	Possible handling discussed: Discussion direction: show the actual pedestrian route and estimated walking time, not just straight-line distance. The earlier discussion used roughly 6–8 minutes each way for 500 metres as an estimate, but customer acceptance was not established.
•	Open question: Still unresolved: the maximum distance customers will accept, whether they will pay for the convenience, and how this changes by destination, weather, time of day, mobility needs and luggage/children.
9. Additional operational and trust risks to investigate
•	Permission and ownership: Does the host own the space or have written authority from the owner, apartment association or property manager to rent it to outsiders?
•	Access mismatch: A booking may be confirmed but a gate/security guard may refuse entry or the customer may not find the correct entrance.
•	Space suitability: The listed bay may not fit the customer's car, SUV, two-wheeler or vehicle height/width.
•	Double booking: A host may list the same space on another platform or promise it to someone offline.
•	No-shows and cancellations: The host may keep a slot unavailable for a customer who never arrives.
•	Damage, theft and disputes: Responsibility for vehicle damage, theft, scratches, property damage or pre-existing damage must be defined.
•	Emergency access: A parked vehicle must not block fire exits, emergency routes, ramps or other vehicles.
•	Privacy and data protection: Vehicle registration, identity, location and booking history are sensitive operational data and should be collected only as needed and protected.
•	Reliability: A marketplace needs enough spaces near a destination at the exact times customers need them; scattered listings may not be useful.
10. Business model ideas discussed
A marketplace commission was discussed as an illustrative model. One example used a 20% platform commission on a completed booking. This was an example for discussion, not a final price or validated margin. Other possible fee structures—such as host subscription, customer service fee or property-level partnership pricing—would need separate evaluation.
Before choosing a model, calculate payment-gateway costs, customer support, refunds, insurance, taxes, verification/operations costs, host payout timing, discounts and customer acquisition costs.
11. Recommended initial pilot direction
•	Start in one compact Bengaluru destination zone rather than launching across the whole city.
•	Prioritise managed commercial properties or authorised parking operators over private residential spaces for the first pilot. This was recommended to reduce access, trust and operational complexity—not because residential participation is permanently ruled out.
•	Try to secure 3–5 authorised property partners and a small, manually verified inventory.
•	Initially use human verification and customer support rather than automating every edge case.
•	Use fixed slots, host buffers, hard return times and host-approved extensions.
•	Measure booking completion, failed entry, late departure, cancellations, customer walking-distance tolerance, repeat usage, host satisfaction and contribution margin.
12. Technology direction previously proposed
The earlier discussion proposed the following possible stack. Treat it as a starting suggestion, not a final architecture decision:
•	Frontend: Next.js + TypeScript.
•	Backend/API: FastAPI + Python.
•	Database: PostgreSQL with PostGIS for location-based queries.
•	Maps and routing: map integration that can show pedestrian routes, walking time and the exact parking entrance.
•	Payments: an India-supported payment gateway; compare fees, refunds, settlements and compliance before selecting one.
•	Operations: admin tools for listing verification, booking management, disputes, support and audit history.
The technical design should not be finalised until the business rules, access process, liability model and pilot scope are clearer.
13. Legal, safety and compliance work required
•	Obtain legal advice on property permissions, host authority, parking/commercial-use restrictions and local rules.
•	Define platform, host and customer responsibilities in clear terms and booking policies.
•	Review Indian data-protection requirements, including the Digital Personal Data Protection framework, for identity, vehicle and location data.
•	Review consumer-protection, payment, tax, refund and grievance-handling obligations.
•	Investigate suitable insurance and clarify whether existing property/vehicle policies cover this use.
•	Create a documented emergency and suspicious-activity escalation process. The app must not promise complete security screening.

# 00 — Combined Project Blueprint

## 1. Project identity

**Name:** ParkPool AI  
**Category:** Intelligent shared-parking marketplace and coordination platform  
**Tagline:** Smart parking. Shared possibilities.  
**Initial market context:** India; a compact Bengaluru pilot is proposed. Phoenix Mall of Asia is an illustrative example from the brainstorming handover, not a confirmed launch partner or location.

## 2. Executive summary

ParkPool AI connects people who need temporary parking with people or organizations that have legally usable, underutilized parking capacity. A driver enters a destination and time window, sees verified eligible spaces, compares price and actual pedestrian route, books a suitable space, follows entrance-specific directions, checks in, parks, checks out and receives a receipt. A host or property manager controls the spaces they are authorized to offer, including rates, operating schedules, owner-use blocks, access instructions and hard departure limits.

The combined version adds a coordination layer that can reason across independent providers and multiple time windows. Deterministic services establish availability and booking truth. A constraint optimizer proposes feasible allocations. AI agents interpret natural-language needs, invoke approved tools, summarize eligible evidence and explain recommendations. Human/user confirmation and backend validation remain mandatory for consequential actions.

## 3. The problem

Parking demand is uneven across both geography and time. Around malls, offices, hospitals, markets and event venues, drivers may face full or inconvenient official parking and spend time searching. At the same time, homes, apartments, offices and commercial properties may have authorized parking capacity that is idle during specific hours.

A basic listing marketplace helps discovery, but it does not fully solve:
- fragmented inventory across independent providers;
- time-window overlaps and provider owner-use periods;
- uncertain arrivals and departures;
- late departures and host hard deadlines;
- cancellations and provider withdrawal;
- vehicle/space compatibility;
- entrance and gated-property access;
- safe pedestrian routes and acceptable walking distance;
- double booking and stale availability;
- trust, liability, incident and dispute processes.

## 4. The solution

### Marketplace foundation
- Driver, host, community manager, commercial operator and admin accounts.
- Verified provider and property authority.
- Facility and parking-space listings with photos, dimensions and restrictions.
- Destination-based discovery and map/list results.
- Price, walking route/time, vehicle fit, amenities and policy comparison.
- Time-bounded reservations, payment integration and receipts.
- Check-in/check-out, extension requests and booking history.
- Reviews, support, disputes and audit history.

### Coordination and intelligence layer
- Shared inventory pools across authorized providers.
- Time-window matching with explicit buffers and owner-use windows.
- Rolling-horizon optimization for future allocation proposals.
- Controlled reallocation for cancellations, changed supply and uncertain arrival/departure.
- Explainable ranking using verified data and explicit user preferences.
- Multi-agent orchestration for complex request interpretation and evidence gathering.
- Demand forecasting only after sufficient historical data exists.

## 5. Example end-to-end scenario

A driver plans to visit Phoenix Mall of Asia tomorrow from 2 PM to 6 PM and has an SUV. They want a space within a tolerable walking distance and a clear route to the actual entrance.

1. Driver enters destination, date/time, vehicle and preferences.
2. Intent workflow extracts structured requirements.
3. Geospatial service retrieves nearby approved facilities.
4. Availability service checks provider schedules, exceptions, holds, bookings and buffers.
5. Matching rules remove incompatible vehicle sizes, unauthorized listings and inaccessible slots.
6. Pricing service calculates the full server-side price.
7. Routing adapter obtains pedestrian route distance/time and entrance details.
8. Review service summarizes eligible completed-booking reviews, if available.
9. Ranking/optimizer orders feasible candidates and provides factor-level explanations.
10. Driver chooses a candidate and explicitly confirms.
11. Booking service creates a transactional hold; payment adapter verifies payment where required.
12. Confirmation, access instructions and navigation are shown.
13. Check-in/access verification records arrival. The host/property controls actual entry.
14. Session end time and extension rules remain visible. Extension requires availability and host approval where configured.
15. Check-out closes the session, payment/refund reconciliation completes, and the driver may review or report an incident.

All example places, times and spaces are illustrative. The platform must not claim live availability unless a real provider integration supplies it.

## 6. User groups

| User | Need | Platform value |
|---|---|---|
| Driver/customer | Reliable parking near destination | Discovery, comparison, booking, navigation |
| Individual host | Monetize authorized idle space | Listing, schedule, earnings, booking controls |
| Apartment/community manager | Control shared inventory and permissions | Managed access, inventory and audit |
| Commercial operator | Improve utilization and bookings | Inventory integration, analytics, operations |
| Admin/support | Keep platform safe and reliable | Verification, dispute and audit tools |

## 7. Product principles

1. **Permission before publication:** an empty space is not automatically rentable.
2. **Backend truth:** database/services, not LLM text, determine availability, price and booking status.
3. **Hard constraints before ranking:** vehicle fit, access, time, provider status and booking integrity cannot be traded away by a high score.
4. **Confirmed bookings are protected:** optimizer cannot silently displace a confirmed customer.
5. **Actual route, not just map pin:** show the correct entrance and pedestrian route where data exists.
6. **Operational safety first:** access, liability, overstay and emergency handling need explicit procedures.
7. **Human approval for sensitive actions:** AI suggestions are advisory.
8. **Evidence over claims:** distinguish live data, provider-reported data, estimates, synthetic data and mockups.
9. **Build modular monolith first:** do not split services prematurely.
10. **Measure before claiming:** performance and originality claims need reproducible evidence.

## 8. Differentiators

### D1. Distributed authorized provider coordination
A common coordination layer for independent private, community and commercial providers, with each provider's authority, access rules and inventory constraints recorded.

### D2. Time-window pooling
A physical space can be allocated to multiple bookings only in non-overlapping time windows, with configured buffers and owner-use blocks.

### D3. Uncertainty-aware allocation
Evaluate changes such as cancellation, provider withdrawal, early departure and late arrival. Reallocation must preserve confirmed booking guarantees and must not pretend uncertainty can be eliminated.

### D4. Hybrid intelligence
LLM agents interpret and coordinate; deterministic services enforce rules; OR-Tools or an equivalent optimizer proposes feasible allocations; the transactional backend commits bookings.

### D5. Evidence-grounded recommendations
Every recommendation factor traces to a source: availability query, price calculation, route result, provider verification, vehicle dimensions or eligible review.

### D6. Experimentally evaluated system
Compare the combined architecture with first-come-first-served, distance-only, greedy and rule-based baselines.

These are proposed differentiators. They are not verified as globally unique or patentable.

## 9. What is not being claimed

- Not the world's first parking marketplace.
- Not the first private parking sharing service.
- Not the first multi-agent parking allocation system.
- Not guaranteed crime prevention or vehicle security clearance.
- Not guaranteed live availability without connected providers.
- Not guaranteed demand prediction without evaluated historical data.
- Not a completed product or commercially validated business.

## 10. Scope

### MVP
- User roles and authentication.
- Provider authorization workflow.
- Facility and space inventory.
- Geospatial discovery.
- Provider schedules and exceptions.
- Availability and conflict prevention.
- Basic weighted ranking.
- Booking hold/confirmation with payment sandbox or mock adapter.
- Admin verification and booking operations.
- Auditable check-in/check-out events.

### Advanced release
- Shared inventory pools.
- OR-Tools time-window optimizer.
- Uncertainty scenario simulation and controlled reallocation.
- Explainable multi-agent workflow.
- Review summaries and policy RAG.
- MCP integrations with scoped tools.
- Demand forecasting after data accumulation.
- Operational analytics and pilot reports.

### Out of scope initially
- Autonomous valet or vehicle movement.
- Unapproved gate/barrier control.
- Guaranteed IoT sensor coverage.
- Production real-money payments before legal/security/provider review.
- Automatic provider approval by AI.
- Automatic towing/clamping or physical enforcement.

## 11. Success definition

The first pilot succeeds only if it demonstrates:
- authorized and reliable supply;
- successful customer entry and completed sessions;
- low conflict and late-departure incidence;
- customer acceptance of route and walking distance;
- host satisfaction and repeat participation;
- positive or improving unit economics;
- measurable value from coordination/optimization over simple baselines.

No target is an achieved result until measured and documented.

# 01 — Project Vision and Originality Assessment

## 1. Product definition

**ParkPool AI** is a proposed autonomous shared-parking coordination platform. It connects drivers with verified private, residential-community and commercial parking supply, and coordinates availability and allocation across providers and time windows.

### Core problem

Parking demand is geographically and temporally uneven. Some drivers cannot quickly identify suitable parking near a destination, while some privately or commercially controlled spaces may be idle at particular times. Existing listings alone do not solve the more difficult coordination problems: uncertain arrival/departure times, provider restrictions, overlapping reservations, dynamic supply changes, and competing user preferences.

### Proposed solution

A web-first, mobile-friendly platform that:
- Discovers nearby parking using geospatial search.
- Compares price, walking distance, amenities, provider trust and verified availability.
- Allows authorized providers to list time-bounded inventory.
- Coordinates shared supply through time-window pooling.
- Uses optimization for constrained allocation.
- Uses specialist AI agents for intent understanding, investigation, explanation and workflow coordination.
- Provides audit trails, human approval and measurable evaluation.

## 2. Is the idea copying?

No single broad idea is owned by one company, and using established product patterns or open technologies is not automatically copying. However, reproducing an existing app's exact interface, branding, text, proprietary data, code or protected workflows would create legal and ethical risks.

The basic marketplace concept is already present in the market. A preliminary search surfaced ParkSaathi, which advertises private residential parking in Bengaluru, allowing hosts to list spaces, set prices and accept requests. Therefore, a simple "find and rent a nearby private parking space" positioning is not differentiated.

Research also predates this project on shared-space allocation, multi-agent parking allocation, dynamic allocation and parking route optimization. The proposed system must build on this literature transparently rather than claim those ideas as new.

## 3. Proposed differentiated contribution

The strongest defensible scope is an integrated, evaluated system for:

1. **Distributed provider coordination:** independent providers, communities and commercial facilities share authorized inventory through one coordination layer.
2. **Time-window pooling:** a physical space can serve multiple bookings across non-overlapping intervals, with explicit buffers and owner-reserved periods.
3. **Uncertainty-aware reallocation:** handle late arrivals, early departures, provider withdrawal, cancellations and changing supply without silently breaking confirmed guarantees.
4. **Hybrid intelligence:** LLM agents coordinate and explain; deterministic services enforce constraints; mathematical optimization performs allocation.
5. **Evidence-grounded recommendation:** every recommendation is traceable to availability queries, prices, distance calculations, verified amenities and eligible reviews.
6. **Explainability and evaluation:** compare the system against simple baselines on utilization, match rate, walking distance, conflicts, response time and operating cost.

These are proposed design contributions. Their novelty as a combination has not been conclusively established by the preliminary web search.

## 4. Competitor landscape

| Product / research | Existing overlap | Implication |
|---|---|---|
| ParkSaathi (Bengaluru) | Private residential parking, hosts listing spots, hourly requests | Direct local competitor for the basic marketplace |
| SpotHero | Parking discovery and reservations | Discovery/booking is established |
| JustPark | Private driveway and commercial parking rentals | Peer-to-peer/private parking is established |
| Parkopedia | Parking information, locations and pricing | Parking information aggregation is established |
| Shared parking allocation research | Allocation of privately shared spaces over time | Time-based sharing is established research |
| Multi-agent parking allocation research | Vehicle/space agents and negotiation/allocation | Multi-agent parking allocation is established research |

Competitor feature sets, availability and market reach change. Verify current product details directly before relying on this table for commercial strategy.

## 5. Product positioning

**Recommended description:**  
"An explainable, multi-agent coordination and optimization platform for distributed shared parking inventory."

Avoid:
- "The world's first AI parking app."
- "The first multi-agent parking system."
- "No competitors exist."
- "Guaranteed real-time parking availability" unless a provider integration actually supplies it.

## 6. Target users

- Drivers seeking parking near a destination.
- Individual property owners with authorized spare parking.
- Apartment and residential-community managers.
- Commercial parking operators.
- Employers and campuses managing time-varying inventory.
- Platform administrators and support staff.

## 7. Business model hypotheses

- Commission on completed bookings.
- Provider subscription for inventory and analytics tools.
- Enterprise/community management subscription.
- Optional promoted listings, subject to transparent labeling.
- Aggregated privacy-protected utilization analytics for authorized customers.

Validate willingness to pay, provider acquisition cost, dispute rates, insurance/liability arrangements and local regulations before selecting a final model.

## 8. Initial market validation

Recommended pilot: one tightly bounded neighbourhood or destination cluster in Bengaluru, after provider and property permissions are secured.

Interview:
- 15–20 drivers with recurring destination parking needs.
- 10–15 private-space owners or apartment representatives.
- 5–10 commercial parking operators.

Validate supply reliability, willingness to share, pricing, safety expectations, access arrangements, no-show rules and dispute handling. Do not assume a space can be shared just because it appears empty.

## 9. Research question

Can a hybrid multi-agent coordination architecture combined with constraint-based dynamic allocation improve parking match rate and utilization while maintaining booking reliability and acceptable latency compared with first-come-first-served and rule-based baselines?

## 10. Preliminary conclusion

ParkPool AI is a valid substantial software engineering and research project. The basic marketplace is not original. The project becomes meaningfully differentiated through its precise coordination problem, provider authorization model, uncertainty-aware allocation, hybrid agent/optimizer architecture, explainability and rigorous comparative evaluation.

- An unauthorized user cannot access another provider's private inventory or customer data.

# 03 — Twelve-Module Architecture

Build these as bounded modules inside a modular monolith first. Each module owns its routes, schemas, services, persistence logic and tests. Avoid premature microservices.

## Module 1 — Identity and User Management
**Submodules:** registration, login, password reset, OTP provider adapter, session/refresh tokens, profiles, role/permission policy, consent, vehicle profiles.  
**Acceptance:** role enforcement tests pass; users cannot access other users' vehicles or bookings.

## Module 2 — Provider and Property Authorization
**Submodules:** provider onboarding, individual/community/commercial types, identity/business verification workflow, authority evidence, property/space permission, provider status, compliance checklist.  
**Acceptance:** unverified or unauthorized inventory cannot become bookable.

## Module 3 — Parking Inventory and Listings
**Submodules:** facilities, spaces, dimensions, vehicle fit, amenities, photographs, rates, policies, listing moderation, provider inventory dashboard.  
**Acceptance:** CRUD, validation, moderation and provider isolation tests pass.

## Module 4 — Geospatial Discovery
**Submodules:** destination search, nearby search, PostGIS radius/bounding search, filters, map/list view, routing adapter, result pagination, availability freshness.  
**Acceptance:** geospatial correctness tests and query latency benchmarks pass.

## Module 5 — Availability and Scheduling
**Submodules:** weekly schedule, date exceptions, blackout periods, provider owner-use blocks, booking holds, expiry, buffers, timezone handling, conflict detection.  
**Acceptance:** concurrency tests demonstrate no overlapping confirmed bookings.

## Module 6 — Recommendation Intelligence
**Submodules:** intent parsing, candidate retrieval, hard-constraint filtering, multi-objective scoring, preference profiles, explanation generation, evidence references.  
**Acceptance:** all recommendations are grounded in candidate records; incompatible spaces are excluded.

## Module 7 — Pooling and Optimization
**Submodules:** pool groups, memberships, time-window matching, rolling-horizon allocation, uncertainty scenarios, fairness/priority policies, reallocation rules, OR-Tools optimizer.  
**Acceptance:** compare to FCFS and greedy baselines; preserve confirmed reservation guarantees.

## Module 8 — Reservation and Payments
**Submodules:** quote service, booking state machine, transactional hold/confirm, payment adapter, webhook verification, idempotency, cancellation, refunds, receipts, notifications.  
**Acceptance:** payment and booking integration tests; replayed webhook does not double-charge or double-confirm.

## Module 9 — Reviews and Trust Intelligence
**Submodules:** eligible reviews, moderation, aggregate ratings, sentiment/themes, anomaly flags, dispute intake, provider trust indicators.  
**Acceptance:** no fabricated reviews; AI flags are advisory and reviewable.

## Module 10 — Multi-Agent Orchestration
**Submodules:** LangGraph state, supervisor/router, specialist nodes, CrewAI bounded crews, typed agent contracts, retry/timeout, human approval, tool allowlists, traces and evaluation.  
**Acceptance:** deterministic workflow tests; failures and tool calls are logged.

## Module 11 — RAG, MCP and Predictive Intelligence
**Submodules:** document ingestion, chunking, embeddings, retrieval, reranking, citations, MCP server/client integrations, demand forecasting, model evaluation, responsible AI.  
**Acceptance:** retrieval answers cite sources; MCP tools have scopes; forecasts have held-out evaluation and uncertainty.

**Submodules:** admin console, user/provider moderation, disputes, operational analytics, audit views, CI, unit/integration/E2E tests, load/security testing, Docker, backups, monitoring, deployment and runbooks.

# 04 — Multi-Agent Architecture: LangGraph, CrewAI, RAG and MCP

## 1. Architecture rule

LangGraph is the primary workflow/state orchestrator. CrewAI is used only for bounded collaborative subtasks. Avoid two competing top-level orchestrators. Agents are not trusted sources of truth: application services and the database own inventory, pricing, bookings and payments.

## 2. Twelve specialist agents

| # | Agent | Responsibility | Preferred implementation |
|---:|---|---|---|
| 1 | Parking Intent Agent | Parse destination, time, vehicle and preferences | LLM structured extraction |
| 2 | Location Intelligence Agent | Interpret place and invoke geospatial/routing tools | Geospatial API + LLM |
| 3 | Availability Agent | Retrieve source-stamped availability | Deterministic service |
| 4 | Parking Matching Agent | Enforce vehicle and provider constraints | Rules/optimizer |
| 5 | Pricing Intelligence Agent | Compare total price and explain price factors | Pricing service + optional model |
| 6 | Review Intelligence Agent | Summarize eligible reviews and themes | LLM with evidence |
| 7 | Pooling Optimization Agent | Coordinate candidate allocation proposals | OR-Tools/optimization |
| 8 | Booking Coordination Agent | Prepare reservation workflow and request confirmation | State machine + approval |
| 9 | Navigation Agent | Provide route and walking directions | Routing provider |
| 10 | Trust and Safety Agent | Surface risk signals and policy issues | Rules + anomaly detection |
| 11 | Demand Prediction Agent | Forecast aggregate demand | Statistical/ML forecasting |
| 12 | Customer Support Agent | Answer using policy RAG and booking context | LLM + RAG |

## 3. Orchestrator workflow

1. Receive user request.
2. Intent agent produces validated structured requirements.
3. Retrieve candidate facilities/spaces from PostGIS.
4. Availability service checks schedules, exceptions, holds and bookings.
5. Matching service applies hard constraints.
6. Pricing and review services enrich eligible candidates.
7. Optimizer/ranker creates ranked candidates.
8. Explanation node creates evidence-backed rationale.
9. User selects a candidate and explicitly confirms.
10. Booking service performs transactional hold/confirmation.
11. Payment adapter verifies payment if required.
12. Navigation and notification tasks execute after confirmed booking.

## 4. CrewAI bounded crews

### Review analysis crew
- Review collector: fetches eligible platform reviews.
- Theme analyst: identifies recurring topics.
- Trust analyst: identifies suspicious patterns for human review.
- Summary writer: produces evidence-linked summary.

### Provider onboarding research crew
- Checklist agent: checks required fields.
- Evidence summarizer: summarizes submitted documents.
- Policy reviewer: identifies missing items.
- Human reviewer: final approval.

Crew outputs are advisory and structured. They do not independently approve providers or take irreversible actions.

## 5. Typed agent result contract

```json
{
  "agent": "parking_matching_agent",
  "task_id": "task_102",
  "status": "completed",
  "candidate_space_ids": ["space_001", "space_002"],
  "hard_constraints_checked": [
    "vehicle_compatibility",
    "time_window",
    "provider_status"
  ],
  "evidence_refs": ["availability_query_88"],
  "confidence": 0.91,
  "requires_human_approval": false,
  "warnings": []
}
```

Do not rely on self-reported LLM confidence as calibrated probability. Calibrate confidence against evaluation data if it is used in decisions.

## 6. RAG

Use RAG for:
- Parking policies and provider instructions.
- Platform cancellation/refund rules.
- User help documentation.
- Safety/accessibility guidance.
- Approved operational manuals.

Pipeline: ingest -> parse -> chunk -> attach metadata/permissions -> embed -> retrieve -> optional rerank -> answer with citations.

RAG must respect document access permissions. Retrieved documents are untrusted content, not executable instructions.

## 7. MCP

Use MCP to expose narrowly scoped tools such as:
- `search_nearby_parking`
- `get_space_availability`
- `get_route_estimate`
- `get_provider_policy`
- `create_booking_quote`
- `request_booking_hold` (with user authorization and server validation)

Payment confirmation, refunds, provider approval and irreversible actions require backend controls and appropriate human/user approval. MCP is an integration protocol, not an authorization system by itself.

## 8. Observability and safety

Log workflow ID, agent, tool name, arguments after redaction, authorization context, result status, latency, token usage, errors and approval state. Do not log passwords, payment credentials, precise location history unnecessarily or full private documents.

## 9. Agent evaluation

Measure:
- Task completion rate.
- Structured output validity.
- Tool selection accuracy.
- Unsupported-claim rate.
- Evidence/citation correctness.
- Human override rate.
- Mean and p95 workflow latency.
- Token/API cost per successful task.
- Recovery after timeout/tool failure.

Compare against a non-agent deterministic baseline. More agents do not automatically mean better performance.

- A confirmed booking is not silently reallocated.

B. Rule-based weighted ranking  
C. Single-agent recommendation  
D. Multi-agent recommendation  
E. Multi-agent recommendation plus pooling optimizer

`score = 0.25*distance_fit + 0.25*price_fit + 0.20*amenity_safety_fit + 0.15*review_fit + 0.15*availability_fit`

# 09 — Security, Privacy and Responsible AI

## 1. Physical-world and property authorization

- Require evidence that a host/community/operator has authority to offer the space.
- Clearly define access instructions, permitted vehicle types, operating hours and owner-use windows.
- Never infer that an empty driveway or apartment slot is available for public rental.
- Do not implement gate unlocking or access-code release without explicit owner/provider authorization and secure integration.
- Define incident, damage, no-show, dispute and emergency procedures with legal review.

## 2. AI boundaries

- AI may interpret requests, retrieve information, compare options and explain recommendations.
- AI must not invent availability, price, ratings, safety claims or provider approval.
- AI must not confirm a booking or payment based only on its own generated text.
- Sensitive/irreversible operations require explicit user confirmation and backend validation.
- Treat user text, reviews, uploaded documents and RAG results as untrusted input.
- Restrict tools to allowlisted actions and least privilege.
- Record agent actions and approval decisions.

## 3. Application security

- Password hashing using a modern password hashing scheme.
- Secure session/refresh-token handling and revocation.
- Role- and resource-level authorization.
- HTTPS in deployed environments.
- Rate limits and abuse protection.
- Input validation and output encoding.
- Parameterized database queries.
- File type/size scanning and safe object storage.
- Webhook signature verification and idempotency.
- Secret manager/environment configuration.
- Dependency and container scanning.
- Backups, restore tests and incident response.

## 4. Location and personal data

- Ask for location permission when needed and explain why.
- Allow destination search without continuous location tracking.
- Minimize retention of precise location history.
- Restrict location visibility to the purpose and role.
- Define retention, deletion and access-request workflows.
- Avoid exposing private residential addresses before an authorized booking stage.
- Assess applicable Indian data-protection law and rules with qualified counsel before launch.

## 5. Fairness and explainability

- Do not use protected or sensitive personal characteristics for parking ranking.
- Make ranking factors visible and configurable.
- Explain why candidates were excluded by hard constraints.
- Provide a route/list alternative to map-only access.
- Audit provider and user complaint patterns.
- Keep AI-generated risk flags advisory and allow human review.

## 6. Payments

Use a regulated payment provider; do not store raw card credentials. Verify signed webhooks server-side, use idempotency keys, reconcile provider transaction state and keep booking/payment state transitions separate. Production rollout requires provider terms, tax/accounting and consumer-protection review.

# 11 — Operations, Pilot, Business Model and Risk Register

## 1. Pilot strategy

Start with one compact destination cluster in Bengaluru, not the entire city. The handover recommends a commercial-property-first pilot with approximately 3–5 authorized property partners. This is a recommendation to reduce access and trust complexity; it does not permanently exclude residential providers.

### Pilot supply
- Prefer managed commercial properties or authorized parking operators at the beginning.
- Obtain written permission from the property owner/manager and document the exact spaces and hours that may be offered.
- Manually verify a small inventory before public bookings.
- Confirm access arrangements with security staff and property operations.
- Keep a human support contact available during pilot hours.

### Pilot demand
Interview 15–20 drivers with recurring needs near the selected destination. Interview 10–15 private-space owners or apartment representatives and 5–10 commercial operators. These are suggested research sample sizes, not existing completed interviews.

## 2. Driver journey and operating controls

| Stage | Driver action | System/operations control |
|---|---|---|
| Discover | Enter destination/date/time | Show approved spaces and data freshness |
| Compare | Review price, route, entrance, fit | Pedestrian route and entrance evidence |
| Book | Select slot and vehicle | Server quote, policy disclosure, transactional hold |
| Confirm | Pay/confirm | Verified payment state; no AI-only confirmation |
| Navigate | Follow route | Route to actual entrance, not only centroid |
| Arrive | Present code/QR if enabled | Host/property controls entry; log verification event |
| Park | Begin session | Record start time and any issue |
| Extend | Request extra time | Only if next booking/owner block allows and host approves where required |
| Leave | Check out before hard deadline | Record departure and session completion |
| Close | Receipt/review/report | Reconcile payment/refund and incident workflow |

QR or booking-code verification is a proposed control, not a guarantee of physical security.

## 3. Host/provider journey

1. Register provider and select provider type.
2. Submit identity/business details and evidence of authority.
3. Submit facility details and exact spaces.
4. Provide dimensions, restrictions, photographs and access instructions.
5. Define availability schedule, blackout periods and owner-use windows.
6. Set buffer and hard latest departure time.
7. Set price and cancellation/extension rules.
8. Admin reviews evidence and activates only authorized inventory.
9. Host monitors bookings, arrival, checkout, earnings and incidents.
10. Host can block future availability under published cancellation rules.

Community managers must provide evidence that they have authority under applicable property/community rules.

## 4. Critical operational policies to define before live bookings

### A. Host authority and property permissions
- What documents establish ownership or permission?
- Does an apartment association, landlord or commercial property manager need to approve?
- Which property rules prohibit outside visitors or commercial use?
- How often must authorization be revalidated?
- Who can revoke a listing and how are future bookings handled?

### B. Access mismatch
- Who greets or authorizes the driver at gated properties?
- What if a security guard has not received the booking?
- What if the actual entrance differs from the map pin?
- Is there an on-call escalation number?
- What refund/compensation policy applies when access fails?

### C. Late departure and overstay
The source handover raises a specific example: a host rents a space until 6 PM but the driver remains at 7 PM while the host needs the space at 6:15 PM.

Proposed controls:
- fixed slots;
- host-defined buffer before the host needs the space;
- hard latest departure time shown before booking;
- reminders before expiry;
- extensions only when the host explicitly approves and no conflicting reservation exists;
- overstay fees and escalation rules disclosed before booking;
- support escalation and incident logging.

Unresolved:
- lawful remedies if a vehicle remains after the deadline;
- liability for host losses;
- emergency access;
- whether any towing/clamping remedy is lawful and who may authorize it.

Do not assume the host may forcibly move or tow a vehicle. Obtain qualified local legal advice and never encourage unsafe confrontation.

### D. Security and suspicious activity
The source handover explicitly raises the possibility that a vehicle could contain dangerous or illegal items. Platform controls may include:
- verify host and authority;
- collect only proportionate booking and vehicle details;
- controlled access/check-in records;
- suspicious-activity reporting and emergency process;
- staff training and documented escalation.

The platform cannot security-clear a vehicle and must not promise that misuse is impossible. Hosts should not inspect dangerous contents or handle a suspected device. Keep people away and contact emergency services/police (112 in India) if there is an immediate threat. Confirm emergency guidance with local counsel/authorities before launch.

### E. Walking distance and route acceptability
The handover questions whether users will walk 300–500 metres. It mentions 6–8 minutes for 500 metres as an estimate only, not validated customer behavior.

Show:
- actual pedestrian route;
- walking time estimate and its source;
- lighting/accessibility/safe-path attributes where verified;
- correct parking entrance;
- weather/covered-path information only where reliable.

Test willingness by destination, time of day, price difference, mobility needs, luggage and family travel. Do not assume a universal acceptable radius.

### F. Space suitability
Record dimensions, height restrictions, vehicle class, turning/access restrictions and charging/covered attributes. Do not recommend an incompatible space even if its score is otherwise high.

### G. Double booking and stale inventory
- Centralize booking inventory in the authoritative database.
- Use transactional holds and exclusion constraints/locking.
- Define inventory synchronization with any external listing channel.
- Display availability source and last-updated time.
- Expire abandoned holds.

### H. Damage, theft and disputes
Define evidence capture, check-in/out condition records where proportionate, support workflow, dispute time windows, responsibility and insurance terms. Do not imply that a rating system substitutes for legal protection.

### I. Emergency access
Never allow a listing or allocation that blocks fire exits, emergency lanes, ramps or required circulation paths. Require property-specific approval and periodic audits.

## 5. Business model hypotheses

Possible revenue:
- commission on completed bookings;
- provider subscription for inventory and analytics;
- enterprise/community management subscription;
- optional promoted listing with clear labeling;
- privacy-protected aggregate utilization analytics for authorized customers.

A 20% platform commission appeared in the brainstorming handover only as an illustrative example. It is not a chosen or validated rate.

### Unit economics model

For each completed booking calculate:

`Contribution = platform revenue - payment fees - host incentives - refunds/chargebacks - support cost - verification/operations allocation - insurance allocation - taxes - acquisition cost allocation`

Track:
- average booking value;
- platform take rate;
- host payout;
- payment gateway fee;
- refund/cancellation rate;
- support contacts per booking;
- provider acquisition cost;
- customer acquisition cost;
- repeat booking rate;
- contribution margin.

Do not finalize pricing until provider interviews, customer tests and payment/tax review are complete.

# Glossary

- **Host/provider:** Person or organization authorized to offer a parking space.
- **Facility:** Property/site containing one or more parking spaces.
- **Parking space/bay:** Physical unit that can be reserved.
- **Pool:** Group of spaces made available for coordinated allocation under agreed rules.
- **Time window:** Start/end interval requested by a driver or offered by a provider.
- **Buffer:** Non-bookable time reserved between sessions or before owner use.
- **Owner-use block:** Period when a provider reserves the space for its own use.
- **Booking hold:** Temporary inventory reservation pending confirmation/payment.
- **Confirmed booking:** Reservation committed by the backend after all required checks.
- **Hard constraint:** Requirement that must be satisfied; cannot be offset by a higher recommendation score.
- **Soft preference:** Ranking preference such as price or walking distance.
- **Rolling-horizon optimization:** Recompute future allocations as new information arrives, while protecting already confirmed reservations.
- **Uncertainty-aware allocation:** Evaluate uncertain arrivals/departures and supply changes using scenarios or probabilistic estimates.
- **LangGraph:** Proposed stateful workflow orchestration framework for agent steps.
- **CrewAI:** Proposed framework for bounded collaborative agent tasks.
- **OR-Tools:** Constraint optimization toolkit proposed for allocation.
- **RAG:** Retrieval-augmented generation; answers use retrieved approved knowledge with citations.
- **MCP:** Model Context Protocol; a tool integration protocol, not an authorization system.
- **PostGIS:** PostgreSQL extension for geospatial data and queries.
- **PWA:** Progressive Web App.

CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE users (
    id UUID PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(255) UNIQUE,
    phone VARCHAR(20) UNIQUE,
    password_hash TEXT,
    is_verified BOOLEAN NOT NULL DEFAULT FALSE,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE user_roles (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR(40) NOT NULL,
    PRIMARY KEY (user_id, role)
);

CREATE TABLE vehicles (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id),
    vehicle_number VARCHAR(30),
    vehicle_type VARCHAR(30) NOT NULL,
    vehicle_length_cm NUMERIC(7,2),
    vehicle_width_cm NUMERIC(7,2),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE providers (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id),
    provider_type VARCHAR(30) NOT NULL,
    business_name VARCHAR(200),
    verification_status VARCHAR(30) NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE facilities (
    id UUID PRIMARY KEY,
    provider_id UUID NOT NULL REFERENCES providers(id),
    name VARCHAR(200) NOT NULL,
    address TEXT NOT NULL,
    location GEOGRAPHY(POINT, 4326) NOT NULL,
    facility_type VARCHAR(40),
    verification_status VARCHAR(30) NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_facilities_location ON facilities USING GIST(location);

CREATE TABLE parking_authorizations (
    id UUID PRIMARY KEY,
    provider_id UUID NOT NULL REFERENCES providers(id),
    facility_id UUID NOT NULL REFERENCES facilities(id),
    evidence_reference TEXT NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'pending',
    reviewed_by UUID REFERENCES users(id),
    reviewed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE parking_spaces (
    id UUID PRIMARY KEY,
    facility_id UUID NOT NULL REFERENCES facilities(id),
    space_code VARCHAR(50),
    vehicle_type VARCHAR(30) NOT NULL,
    max_length_cm NUMERIC(7,2),
    max_width_cm NUMERIC(7,2),
    covered BOOLEAN NOT NULL DEFAULT FALSE,
    ev_charging BOOLEAN NOT NULL DEFAULT FALSE,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    hourly_price NUMERIC(10,2) NOT NULL CHECK (hourly_price >= 0),
    currency CHAR(3) NOT NULL DEFAULT 'INR',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(facility_id, space_code)
);

CREATE TABLE availability_schedules (
    id UUID PRIMARY KEY,
    parking_space_id UUID NOT NULL REFERENCES parking_spaces(id),
    day_of_week SMALLINT NOT NULL CHECK(day_of_week BETWEEN 0 AND 6),
    start_time TIME NOT NULL,
    end_time TIME NOT NULL,
    buffer_minutes INTEGER NOT NULL DEFAULT 15 CHECK(buffer_minutes >= 0),
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CHECK(start_time < end_time)
);

CREATE TABLE availability_exceptions (
    id UUID PRIMARY KEY,
    parking_space_id UUID NOT NULL REFERENCES parking_spaces(id),
    starts_at TIMESTAMPTZ NOT NULL,
    ends_at TIMESTAMPTZ NOT NULL,
    exception_type VARCHAR(30) NOT NULL,
    reason TEXT,
    CHECK(ends_at > starts_at)
);

CREATE TABLE pool_groups (
    id UUID PRIMARY KEY,
    provider_id UUID REFERENCES providers(id),
    name VARCHAR(150) NOT NULL,
    description TEXT,
    status VARCHAR(30) NOT NULL DEFAULT 'active',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE pool_memberships (
    id UUID PRIMARY KEY,
    pool_id UUID NOT NULL REFERENCES pool_groups(id),
    parking_space_id UUID NOT NULL REFERENCES parking_spaces(id),
    valid_from TIMESTAMPTZ NOT NULL,
    valid_until TIMESTAMPTZ,
    status VARCHAR(30) NOT NULL DEFAULT 'active',
    CHECK(valid_until IS NULL OR valid_until > valid_from)
);

CREATE TABLE bookings (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id),
    vehicle_id UUID NOT NULL REFERENCES vehicles(id),
    parking_space_id UUID NOT NULL REFERENCES parking_spaces(id),
    start_time TIMESTAMPTZ NOT NULL,
    end_time TIMESTAMPTZ NOT NULL,
    status VARCHAR(30) NOT NULL CHECK(status IN
        ('held','confirmed','occupied','completed','cancelled','expired','no_show')),
    total_amount NUMERIC(10,2) NOT NULL CHECK(total_amount >= 0),
    currency CHAR(3) NOT NULL DEFAULT 'INR',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK(end_time > start_time)
);
